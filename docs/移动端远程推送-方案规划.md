
# 移动端「杀进程后仍收到消息」远程推送 —— 方案规划

## 1. 现状与问题
- 当前通知依赖 WebSocket 实时连接（services/notifications.ts + wslink.ts）：app 前台/后台（未被杀）时，WS 收到消息 → 本地弹系统通知 + 未读+1。
- **app 被系统/用户杀掉后，WS 断开，无法接收任何消息** → 没有推送通知。
- 用户重新打开 app 后，会通过已有的「离线消息增量同步」（loadOfflineMessage / 会话历史）拿到期间消息——**消息不丢，只是「被杀时没有实时通知」**。
- 当前 APK 为 debug 签名、本地 gradle 构建，未接任何推送厂商（无 FCM、无 Expo push token、无 google-services.json）。

## 2. 目标
杀进程后 → 系统弹远程推送通知 → 点击通知直接进入对应会话。

## 3. Android 推送的根本约束
被杀后要收远程推送，必须依赖系统级推送通道（推送进程常驻）。Android 可选：
| 通道 | 被杀后可达 | 中国大陆可用 | 依赖/成本 |
|---|---|---|---|
| FCM (Firebase) | 是 | 否：国行多无 Google 服务 | google-services.json、Play 签名 |
| Expo Push Service | 是 | 一般：国内连通性/稳定欠佳 | EAS 云构建、Expo servers 在线 |
| 厂商推送（华为/MI/OPPO/vivo） | 是 | 是 | 每厂商 SDK+申请+证书 |
| 极光 JPush / 个推 getui 聚合 | 是 | 是 | 第三方 SDK+AppKey，服务器对接 |
| 自建轮询/保活 | 否（仅重开拉消息） | 是 | 零额外依赖，达不到杀后弹通知 |

结论：国内自用、杀后可弹通知，现实选型是「厂商推送」或「极光/个推聚合」；FCM 仅当目标设备有 Google 服务。

## 4. 推荐架构（以极光/个推或厂商为推送通道）
发送端APP -> 合鸣server -> (在线: Mobile WS 实时 / 不在线或被杀: 推送服务SDK -> 通道 -> 系统拉起App弹通知 -> 点击进会话)

端到端流程：
1. 注册：app 启动获取推送 token，上报绑定当前用户设备。
2. 判定：server 收消息时判断收件人是否在线（复用 hub.getOnlineDeviceIds）。
   - 在线 -> 现有 WS 实时推送。
   - 不在线/被杀 -> 走推送通道向该用户设备推送（发送者+摘要+convId）。
3. 送达：系统级推送拉起 app -> 弹系统通知（channel）。
4. 回跳：点击通知 -> notification response 携带 convId -> 打开会话 + 拉离线消息。

## 5. 服务端改造（server）
- 数据：devices 表加 push_token / push_provider / push_registered_at（或新表 push_devices）。
- 新 API：POST /api/devices/push-token（上报/绑定）、注销。
- 推送判定：在发消息路由里对不在线收件人调用推送服务；统一「在线判定」复用 hub。
- 推送适配层：封装 provider 接口（发送/回执/失败日志），实现所选 provider 客户端。
- 配置：AppKey/AppSecret 走环境变量，不入库。

## 6. 移动端改造（mobile）
- 依赖：expo-notifications（已有）+ 推送 SDK（jpush-react-native / getui 或厂商 SDK）；获取 push token 需 expo-device、expo-constants。
- 注册：启动获取 token -> 上报绑定当前用户；登出解绑。
- 离线被拉起：getLastNotificationResponse / 通知点击回调 -> 用 convId 跳转会话并拉离线消息。
- 通知渠道：复用 messages，为高优先级/被@ 新增 channel。
- 设置页：NotificationSettingsPage 增加「远程推送」开关与状态说明。

## 7. 变体（暂不接第三方 SDK）
- 方案A（最小）：仅完善「重开 app 后提醒未读」（启动时有未读弹一条本地通知）。零依赖、易交付，非即时杀后推送。
- 方案B：接 Expo Push Service（国内连通性优于 FCM，但依赖 Expo servers 与 EAS 云构建）。

## 8. 工作量与风险
- 第三方推送（极光/厂商）：server 适配 1-2 天 + 移动端 SDK 1-2 天 + 平台申请证书 1-3 天（部分需企业资质/审核）。
- 风险：① 国内通道申请需企业开发者资质；② debug 签名 APK 无法接 FCM/部分厂商（需正式签名 build）；③ 各厂商保活/权限限制不同；④ 推送按量收费。
- 决策点：推送通道选型（厂商 vs 极光/个推 vs FCM/Expo）、是否有企业开发者资质。
