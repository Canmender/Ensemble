# 合鸣 Ensemble 主体工程分析报告（移动端 + 服务端 + Web）

> 定位：对 D:\MultiAgent 合鸣主体工程（desktop/packages/server、web、shared 与 mobile/src）做现状分析，聚焦安全/健壮性、IM 能力、数据模型，并给出方案。
> 说明：结论均来自对源码的阅读，标注文件与函数。

---

## 0. 总体评价

合鸣工程的安全基座明显强于之前分析的两个第三方案例（box-im / V-IM）：
- 密码 scrypt + salt + timingSafeEqual；会话 token 32 字节随机，30 天过期（db/users.ts）。
- WebSocket Hub 鉴权 + wildcard 订阅禁用 + 1MB payload + 背压 + 批量发送 + 异地登录踢线（api/ws/hub.ts）。
- 消息访问控制 canAccessConv 按会话归属/参与者隔离；撤回/已读/搜索多数端点做了越权检查。
- 上传 100MB 上限 + MD5 去重 + 安全扩展名 + 日期目录（api/routes/upload.ts）。

但存在若干授权与健壮性缺口，见下。

---

## 1. 【高危】群聊管理缺乏 owner/admin 权限校验（授权提升）

位置：desktop/packages/server/src/api/routes/conversations.ts

- 建群时写入群主：`r.post("/")` 内 `setConversationGroupOwner(id, req.user.id)`（L144）。
- 但修改群信息端点 `r.patch("/:id")`（L386 起）只调用 `canAccessConv(conv, req.user?.id)`（L386 前一行）做归属判断，**没有**校验当前用户是否为群主或群管理员。
- `canAccessConv` 对 group 类型返回：`!conv.userId || conv.userId===userId || participantIds.includes(userId)` —— **任何一个群成员都能通过**。

影响（任意普通群成员可做到）：
1. 把自己加入 groupAdmins：`body.groupAdmins` → `setConversationGroupAdmins` —— 自封管理员。
2. 开启全体禁言：`body.groupMuted=true` → `setConversationGroupMuted` —— 一个人禁掉整个群。
3. 增删成员：`body.participantIds` → `updateConversationParticipants`（可把群主踢掉）。
4. 改群名/公告。
5. 甚至 `DELETE /:id` 仅校验 canAccessConv（L467），任意群成员可解散/删除整个群会话。

方案：
- 为 group 类型引入 owner/admin 判定：`canModerateGroup(conv, userId)` = 是 owner 或在 group_admins 列表；
- groupMuted / groupAdmins / participantIds / announcement / DELETE 走此判定；
- 只有 owner 可改 groupAdmins 与踢群主；admin 可管理成员/公告/禁言，但不可改 groupAdmins 自身。

## 2. 【中危】共享 Agent 会话的越权可读

位置：conversations.ts 顶部 `canAccessConv` 末分支：
- 非 user 会话、非 group（即 Agent 直聊）时：`return !conv.userId || conv.userId === userId`。
- 对 `userId === ''` 的共享 Agent 会话（多用户共享 run），**任何已登录用户只要知道 conv id 即可读历史/发消息**（/messages 与 /search）。
- 会话不在个人列表（listConversations 按 userId 过滤），但 id 可枚举/猜测（newId 随机，难度中等），多租户云部署下为隐患。

方案：共享 Agent 会话改为显式 participant/ACL，或标注为只读；云部署建议关闭匿名共享 run 的可发现性。

## 3. 【中危】撤回判定 agentId 语义歧义

位置：conversations.ts `DELETE /:id/messages/:msgId`：`const mine = msg.agentId === req.user?.id || msg.agentId === "user";`
- 若一条消息 agentId 恰好等于发送者的用户 id（命名空间相同为 user_ 前缀），或任意 agentId 为 "user" 的系统提示，可能被误判为可撤回/不可撤回。
- 建议：直接查 chat_messages 行的 user_id（若已按发送者落库）做归属判定，业务确权。

## 4. 【中低】群禁言只拦“非 user 会话”

位置：`POST /:id/messages`：`if (!conv.runId.startsWith("conv_") && conv.groupMuted)`。
- 用户-用户群（runId 以 conv_ 开头）不走禁言检查；但纯用户群也可能想禁言。建议对纯用户群按 groupMuted 同样拦截，并排除管理员。

## 5. 【中低】全局消息搜索 N+1 查询

位置：conversations.ts `GET /search`：遍历 `convs.slice(0,50)`，对每个会话调 `searchChatMessages(c.runId, q)`。
- 每次命中会话都可能做一次 LIKE 全扫；最多 50 次，无并发/超时。会话多时卡顿。
- 建议：LIKE 加 limit + 合并为单次 SQL + 限制最大扫描时长；或将搜索结果缓存。

## 6. ws hub 会话 token 与 x-forwarded-for 说明

位置：api/ws/hub.ts
- `_sessionToken` 是单个共享 token（启动时生成，/api/ws-token 暴露）——本地单机无碍，但云多租户场景应禁用共享 token 直连，仅允许用户 session token。
- `extractIp` 直接信任 x-forwarded-for 首个值——若用于限流/审计会被伪造。建议做代理白名单或在可信网关取 remoteAddress。

## 7. 数据模型评价

位置：desktop/packages/server/src/db/sqlite.ts

- 表结构合理：users/sessions/agents/tasks/runs/jobs/run_events/chat_messages/conversations/conversation_reads/devices/upload_files/workflows。
- 索引：chat_messages(run_id)、conversations(user_id)、conversation_reads(user_id)、jobs(run_id,agent_id)、run_events(run_id,job_id)、devices(user_id)、upload_files(md5)。
- 迁移策略（migrateUserColumns）对旧库逐列补齐 + 重建 chat_messages 去外键，健壮。
- 建议：chat_messages 增加 (run_id, ts) 复合索引以支持历史分页/搜索；conversations 增加 (user_id, pinned, updated_at) 支持置顶排序。

## 8. 移动端（mobile/src）健壮性观察

- services/wslink.ts：原生 WS 封装，支持 token 直连/回退 /api/ws-token、心跳、指数退避重连（reconnectDelay 递增）、手动关闭标记、全局聊天消息监听——健壮性优于 box-im im-web。
- store/unreadStore / chatTargetStore / meStore / deviceStore：会话/未读/头像/设备状态集中管理；建议确认未读记数在“收到新消息”与“进入会话清零”之间的幂等与多端同步。
- 说明：按 mobile/AGENTS.md 与 CLAUDE.md，移动端基于 Expo v57；任何改动先查 https://docs.expo.dev/versions/v57.0.0/。
