## 一、`ms()` 丢失：存在性在合并中被静默翻转

**事实**：`mobile/src/theme.ts` 的 `ms()`（`:258` 现已恢复导出）曾整段消失，
导致 20+ 文件 import 它却解析不到，编译直接失败。修复见 `0790abf`。

**为什么会这样**：不是某次重构主动删除，而是 **8-22~8-27 期间多分支并行、
反复合并**的过程中丢失。同期还有 reanimated 迁移、native 模块接入等多个
并行分支在改同一批文件。

**为什么全程零报错**：git 在合并时对「删除一个已被双方引用的导出」不产生冲突
——只要另一分支没同时改那个文件的同一区域，git 认为合并干净。**代码能编译
与否和 git 认为有没有冲突，是两件不同的事。**

**防止复发的措施**：
- ✅ 已有：移动端 CI typecheck 门禁（`2bd1143`）。今天它一次就抓出 9 条
  TS2339 + 3 条 zod 缺失，说明该类问题一旦进入仓库就会被拦。
- ✅ 已有：`.claude/worktrees/` 已加入 `.gitignore`（`9e01028`），
  杜绝 worktree 副本被误提交进主仓库。
- ⚠ **目前无自动门禁能发现「历史性丢失」**：CI 只能保证「此刻的代码能编译」，
  无法知道它曾经丢过什么。历史结论只能靠 git 历史复核。

## 二、CI 门禁残缺才是根因

**事实**：修复前 `.github/workflows/ci.yml` 的 typecheck job
只跑 `--filter @ensemble/shared typecheck && --filter @ensemble/server typecheck`，
**web 与 desktop 两个包完全不在门禁内**；build job 跑 shared/server/web，
**漏了 desktop**；整个文件对 mobile 零引用（`grep -c mobile ci.yml = 0`）。

**为什么会这样**：门禁是逐步加的——每次修一个包的构建失败就补一个 job，
没人回头核对「所有包都被覆盖了吗」。**缺口的成因是没有人维护清单，不是某次写错。**

**这一条为什么排在根因位**：第一条（`ms()` 丢失）只是症状，
真正让它进 main 的是 CI 从不检查 mobile。若当时有 mobile typecheck，
它在合并那一刻就会红。

**防止复发的措施**：
- ✅ 已有：`7e225b2` 补齐——typecheck 改为 `pnpm -r typecheck`（递归覆盖全部包，
  且新增包不会被漏）、build 补 desktop、`2bd1143` 新增 mobile-typecheck job。
- ⚠ **三个 job 仍不覆盖 relay-server**（独立 npm 工程，有自己的
  `test/auth.test.cjs`，但未接进 CI）。这是已知的剩余缺口。

## 三、衍生产物会过期，而 tsc 没有理由报错

**事实**：`packages/shared/design/tokens.json`（单源）改了之后，
`mobile/src/design/generated/tokens.ts`（产物）没有重新生成，滞留旧值两个月。

**为什么会这样**：生成器 `desktop/scripts/build-tokens.mjs` **不在任何
构建流程里**——`pnpm build` 不调它、CI 不调它、pre-commit 也不调它。
它是纯手工工具，只有记得跑的人才会跑。

**为什么 tsc 查不出**：产物**类型完全合法**。`tokens.ts` 里
`primaryFg: "#FFFFFF"` 是一个合法的字符串字面量，tsc 没有理由说
「这个值和 tokens.json 里的不一致」——**一致性和类型合法性是两件事**。
准确的说法是「类型合法所以 tsc 无理由报错」，而不是「tsc 查不出所有问题」。

**git 历史证据**：扫描每次改单源的提交，发现
`679f886` 同步改了产物，而 `b7eeaa2` 与 `e3b707e` 只改了单源——
**这个失效模式历史上至少发生两次，不是一次**。

**防止复发的措施**：
- ✅ 已有：`.githooks/pre-commit`（`38c5b0e`）拦「改了单源但产物未同批暂存」。
- ⚠ **CI 层无门禁，且我实测过为什么**：方案「CI 里跑生成器 + `git diff --exit-code`」
  实测 **exit=0，抓不到漏**（生成器先跑会按当前单源重生成，产物随即变成一致，
  diff 恒为空）。CI 只能查出「单源与产物在同一 commit 内不一致」，
  查不出「两者都没提交」——后者是工作区状态，只有 pre-commit 钩子能覆盖。
- ❌ **产物指纹方案未做**（生成器写入单源哈希，CI 做语义比对）。
  成本高于当前收益，记为待办。

## 四、失效文档比死代码危险

**事实**：仓库里三份审计报告（`docs/audit-cross-cutting-2026-09-05.md`、
`analysis-architecture-2026-09-05.md`、`audit-backend-2026-09-04.md`）的
**状态断言已全部反转**——它们描述的是当时的问题，而这些问题早已被修复。

**为什么危险**：照着报告执行 `git checkout <commit>` 会把已修复的代码
**回退到未修复的状态**。今天审测就差点这么做了。

**为什么会这样**：审计文档写于问题发生时，修复之后没有回标状态。
文档变成了「历史快照」，但读者会当它是「现状说明」。

**防止复发的措施**：
- ✅ 已有：约定审计结论要标注「截至 YYYY-MM-DD 实测」（今天已应用到
  tokens.ts 那条，措辞从「已修复」改为「机制缺陷仍存在，但当前这一例已修复」——
  后者更准确，因为「已修复」暗示当时修过，实际是当时结论本身不准确）。
- ⚠ **目前无自动门禁**：靠人工在审计文档开头标注日期与复核状态。

## 五、可达性缺口不被任何检查覆盖

**事实**：群成员管理页与群公告页有路由、有页面、调的 API 全部可用且已挂载，
**但全仓库没有任何跳转指向它们**；AgentsPage（571 行，创建智能体的唯一界面）
有路由但不在 `NAV_ITEMS` 里。

**为什么会这样**：页面与路由是分开写的，写完页面忘了加入口；
而「入口」这件事没有任何工具会检查。

**为什么现有检查都发现不了**：
- **typecheck 只保证代码能编译**——它不知道路由有没有被链接到
- **单测只保证逻辑对**——测的是函数，不测「用户能否点到」
- **端到端测试当时不存在**

这是**质量体系的结构性盲区**：三个环节各自都对，但没有一环负责「可达」。

**防止复发的措施**：
- ✅ 已有：两处入口已修（`2ca9505`/`d75ec61`），并在
  `docs/PRE-RELEASE-CHECKLIST.md` 列为 B7a/B7b，排在验证顺序第 0 步。
- ⚠ **决策：做成测试而非脚本**（统筹已定，打包后第一批）。
  形态是检查双向：每个 `<Route path>` 是否有入口 / 每个 `NAV_ITEMS.to`
  是否有对应路由。放进 server 的 vitest 才能被 CI 自动跑到。

## 六、注释写「不静默」而实现是 `console.warn`

**事实**：`build-tokens.mjs` 注释写「目录不存在时报错并提示，不静默」，
实现却是 `console.warn` 后继续、退出码仍为 0。
同样的形态在 `scripts/backup.sh` 也有——备份路径写错导致备份了一个
不存在的库，脚本静默成功，「备份一直在跑」这个前提不可信。

**为什么会这样**：注释与实现是两个人（或两个时期）写的，改实现时没改注释。
注释描述的是**意图**，读者会把意图当事实。

**防止复发的措施**：
- ✅ 已有：`50cc0c0` 改为 throw + 非零退出码 + 错误信息写明后果与重跑指引；
  `7b9994f` 修 backup.sh 路径并加「源库存在性 + 核心表齐全 + 完整性检查」
  三重校验（**注意：不能用文件大小判断空库——实测空 SQLite 库有 12288 字节**）。
- ⚠ **目前无自动门禁**：注释与实现的一致性靠人工评审。

## 七、判「成员是否存在」必须把生成产物纳入搜索范围

**事实**：`primaryFg` 是在 `tokens.ts`（**生成产物**）里真实存在的 token，
手写的 `theme.ts` 里 `Palette` 接口没接住它，类型检查因两处都声明而通过。
今天这条被误判为「属性凭空发明」，直到核实 `tokens.ts:11,36` 才发现它是真实存在的。

**为什么会这样**：搜索「某成员是否存在」时，若只在源码目录搜，
会漏掉**构建期生成的产物**——那里可能有真实定义，也可能有过期值。

**怎么防止**：判断「某成员是否存在」时，
**必须把生成产物一并纳入搜索范围**；判断「值对不对」时，
还要确认产物是否与单源同步（见第三节）。

**防止复发的措施**：
- ⚠ **目前无自动门禁**：靠人工核实。已把这条写进
  `VERSIONING-SOP.md`（`bb23fb6`「真值映射遗漏」审计规则）。

## 附：一句话总结

今天七条里有五条（③④⑤⑥⑦）的共同点是——**存在一个「人以为有门禁、
实际没有」的地方**。CI 跑了一些检查，但覆盖面比人以为的小；
注释写了一些保证，但实现比注释松。
**排查问题时值得先问一句「这里真的有人在管吗」，而不是「它看起来有人管」。**
