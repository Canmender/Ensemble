# 团队权限 O1 生产落地手册

> 编制日期：2026-08-24 | 前置：《团队与权限体系设计》；本篇是 O1 期的逐文件实施手册
> 生产环境事实（已核实 origin/main @ 22416ee+）：
> - `users` 表**已有 role 列**（`TEXT DEFAULT 'user'`），但注册永远写 `'user'`、全代码库无任何权限检查消费它——**沉睡字段，本方案激活之**
> - 认证中间件已注入 `req.user = {id, username, role}`（auth.ts:117 的 system 角色是机器凭证）
> - 迁移机制现成：sqlite.ts 的 `migrateUserColumns()` 用 PRAGMA table_info 探列 + ALTER TABLE 增量补列（avatar_url 先例）
> - 生产部署走 DEPLOY.md 标准流程（swap→fetch 重试→核对版本→reset→compose build），数据在命名卷不受 reset 影响

## 一、角色模型落地（兼容优先）

### 1.1 角色枚举与存量映射

```ts
// shared/src/types/org.ts 新建
export type OrgRole = "owner" | "admin" | "moderator" | "member" | "guest";
```

**存量用户迁移策略（生产库已有真实用户，不能动他们的登录）**：

- 现有值 `'user'` → 读时映射为 `'member'`（代码层 `normalizeRole()`，不刷库——零风险）；
- **首个注册用户自动成为 owner**：`createUser` 里查 users 表 count==0 时写 `'owner'`（新部署即开箱有管理员）；生产库已有多个用户 → 部署后由第一个自升级行为或 SQL 手工指定 owner（提供一次性 CLI：`node scripts/set-owner.mjs <username>`，进容器执行）。

### 1.2 权限中间件

```ts
// api/auth.ts 增加（与 apiAuth 同层）
export function requireRole(...allowed: OrgRole[]) {
  return (req, res, next) => {
    const role = normalizeRole(req.user?.role);
    if (!allowed.includes(role)) return fail(res, new Error("需要更高权限"), 403);
    next();
  };
}
```

挂载示例：部门 CRUD 路由 `requireRole("owner","admin")`；成员管理同上且**服务端强制"不能操作同级及以上"**（改角色/禁用前比对目标用户 role 排序）。
机器凭证（role:"system"）**不得**通过 requireRole——明确排除，延续"清单即权限"的认证哲学。

## 二、Schema 增量（全部走既有 migrateUserColumns 模式）

```sql
CREATE TABLE IF NOT EXISTS departments (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  parent_id TEXT REFERENCES departments(id),
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS organization (
  id TEXT PRIMARY KEY, name TEXT NOT NULL,
  settings_json TEXT, created_at TEXT NOT NULL
);
-- users 补列（探列式，幂等）
ALTER TABLE users ADD COLUMN dept_ids TEXT;      -- JSON [主部门,...兼职]
ALTER TABLE users ADD COLUMN title TEXT;
ALTER TABLE users ADD COLUMN status TEXT NOT NULL DEFAULT 'active';
-- 会话关联
ALTER TABLE conversations ADD COLUMN dept_id TEXT;
ALTER TABLE conversations ADD COLUMN visibility TEXT NOT NULL DEFAULT 'members';
```

注意点：
- SQLite 的 ALTER TABLE ADD COLUMN 带 REFERENCES 不强制外键约束（PRAGMA foreign_keys 默认关），树完整性由应用层校验（防环：parent 链检测）；
- `status='disabled'` 的用户在 `resolveUser`（token 校验处）直接拒绝——禁用立即生效于 WS 与 REST 两通道。

## 三、API 面（新增 routes/org.ts，~150 行）

| 端点 | 权限 | 说明 |
|---|---|---|
| GET /api/org/members?dept=&status= | member+（guest 拒绝） | 成员目录 |
| POST/PATCH/DELETE /api/org/departments | admin+ | 部门 CRUD（删部门时成员置回未分组而非级联删）|
| PATCH /api/users/:id | admin+ 且目标 role < 自己 | 改 role/status/dept/title；Owner/Admin 不可被 Admin 改 |
| POST /api/org/init | 首次调用无守卫，之后 admin+ | 幂等初始化 organization 单例 |

注册流程改动：`createUser` 加首用户判定（见 1.1）；登录响应带 role（前端据此显隐管理入口）。

## 四、双端 UI（O2 内容，此处只定契约）

- 登录/会话响应新增 `role` 字段——客户端按 role 显隐「管理」入口；
- 通讯录页请求 `/api/org/members` 渲染部门树（dept_ids 为空进「未分组」组）；
- 本期不做 Guest 的受限模式实现（schema 和角色位先留好，UI 后续期）。

## 五、生产部署序列（关键差异：这次有 schema 变更）

1. 开发分支完成 O1 → 测试（本地单测 + 云端 staging 无，直接按云端唯一测试环境共识：合入 main 前桌面会话自跑完整 API 冒烟）；
2. 合入 main → 桌面会话按 DEPLOY 流程部署 v0.8.32+；
3. **部署后立即执行**：`docker exec ensemble-server node scripts/set-owner.mjs <你的用户名>`（一次性把现有账号提为 owner）；
4. 探针验证三件：普通用户调部门 CRUD 得 403 ✓ / owner 调得 200 ✓ / disabled 用户登录被拒 ✓；
5. 移动端/桌面端旧版本对新增字段的兼容性确认（旧客户端忽略未知 JSON 字段，天然兼容——但要在发新版说明里标注）。

**回滚预案**：schema 全增量、零破坏性变更（无删列/改类型）——回滚 = revert 代码重部署即可，旧代码忽略新表新列。这是选探列式增量的根本原因。

## 六、风险与边界

| 风险 | 对策 |
|---|---|
| 存量用户全是 member，没人能管 | set-owner.mjs 一次性脚本 + 文档写明 |
| Admin 提权攻击（A 改 B 为 admin 再借 B 之手）| 服务端硬规则：只能授予 ≤ 自身等级的角色；操作审计留 run_events 式日志表（org_audit，O1.5 可加） |
| 部门树成环导致渲染死循环 | 创建/改父级时沿 parent 链检测，遇自身即拒 |
| 多端并发改同一用户角色 | UPDATE 带 updated_at 条件（乐观锁），冲突返回 409 |

## 七、工时与分派建议

- 桌面会话：shared 类型 + 中间件 + org.ts 路由 + 迁移 + set-owner 脚本 ≈ 2 天；
- 移动会话：通讯录页改造吃 /api/org/members ≈ 1.5 天（O2 前半）；
- 桌面 web 通讯录改造 ≈ 1 天；
- 部署与探针验证：桌面会话随提交做。

顺序：两端 bug 修复（任务 #1/#2）完成后立即启动 O1 服务端部分——它是纯增量，可与移动端 UI 并行。
