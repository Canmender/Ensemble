# 用户主权插件体系：云端只做中转，功能与界面归每个用户

> 编制日期：2026-08-23 | **宗旨修订**：推翻《插件跨端同步机制》隐含的"服务端装、全员共享"模型
> 用户原话锚定："云端只做中转，每个用户的界面和功能都可以不一样，他们都可以自己定制。如果在云端定死了，违背了我们的自定义宗旨。"

## 一、模型对比：为什么必须倒过来

| | 旧模型（已废弃） | 新模型（用户主权） |
|---|---|---|
| 插件装载者 | 服务器管理员 | **每个用户自己** |
| 插件可见性 | 全员共享同一套功能 | A 装了投票，B 没装——B 看到的投票卡是降级文本 |
| 云端角色 | 功能宿主 | **纯中转 + 按用户隔离的运行沙箱** |
| 界面差异来源 | 无（人人相同） | 用户自己的插件集 + 自己的主题 + 自己的卡片 |

这个模型恰好与合鸣的多租户底座吻合：业务表全部带 user_id（store.ts 已核实），认证体系有 per-user token——缺的只是把"设置"和"插件"也纳入 user 维度。

## 二、架构：多租户插件运行时 = Cordis isolate 的教科书场景

### 2.1 核心结构

```
云端 server
└─ root Context
   └─ ctx.isolate('plugins', Symbol(`user:${userId}`))   ← 每用户一个作用域
      ├─ 该用户启用的插件 fiber 们（互不影响）
      ├─ ctx.isolate('storage') 内的 plugin_kv 按 (userId, pluginId) 双键隔离
      └─ 用户卸载/禁用某插件 → dispose 该子树 → 其他用户零感知
```

这正是 Cordis 调研里 isolate 的设计意图：**同名服务在不同作用域各有独立实例**。"poll 插件"在用户 A 和用户 B 的作用域里是两个独立 fiber，各自配置、各自生命周期。

### 2.2 插件代码的分发 vs 实例化

关键区分：
- **插件包（代码）**：全局唯一，存云端插件仓库（对象存储/目录），按需下载——类似 npm registry 与 node_modules 的关系；
- **插件实例（fiber）**：per-user，用户"安装"= 在自己的 isolate 作用域里 mount 一份实例；"卸载"= dispose。

云端为用户 u 运行插件时才实例化 → 冷启动延迟由两点缓解：常用插件常驻池（LRU 卸载最久未用用户的空闲插件）；信封协议天然异步无强延迟敏感。

### 2.3 执行位置的三元结构（修订版）

```
【云端实例】用户从市场装的通用插件 → 云端该用户 isolate 内执行
             （聊天管线拦截、定时任务、REST 动作都在这里）
【桌面实例】桌面专属插件（本机文件访问、本地命令）→ 桌面端执行，
             经 device-link 的 action 白名单转发给手机用（上一份文档的机制保留）
【手机端】  纯渲染 + 动作转发：卡片模板内置 shared 包，动作按 host 分派
```

三处执行、一套清单协议（PluginDescriptor 加 `userId` 字段），同步机制不变。

## 三、必须补的基建：settings 从全局变 per-user

现状核实：`AppSettings` 是全局单份（settings.ts 无 user 维度）。改造：

1. SQLite 增量迁移：`user_settings(user_id, key, value_json)` 新表（不动现有全局 settings——它降级为"默认值层"）。
2. 解析链：**user_settings → 全局 settings → schema 默认值**（三层合并，正是 Cordis intercept 配置解析链的同构）。
3. settings API 带 `req.user.id` 写读（auth 中间件已在所有路由前，改造成本低）。
4. 主题自定义方案（S3 的 accentId 等）直接落进 user_settings——主题本来就是 per-user 的。

## 四、对既有各方案的连锁修订

| 文档 | 修订 |
|---|---|
| 插件化重构实施手册 R4 | 管理 API 从 `/api/plugins` 改 `/api/users/me/plugins`；PluginHost.loadAll 变为「全局包仓库扫描 + 按请求的用户 isolate 实例化」 |
| 功能插件系统方案 §3.3 | KV 隔离从 (pluginId) 二元变 (userId, pluginId) 三元键 |
| 插件跨端同步机制 | PluginDescriptor 加 userId；桌面端同步的只是"该登录用户"的清单视图 |
| 用户插件 UI 方案 T1/T2 信任分级 | "管理员审批"弱化为"首次安装时权限同意"（用户即管理员）——市场源白名单仍由部署者控制（这是运营边界不是产品边界） |
| 手机桌面互联 L2 配对 | 配对关系本身是 per-user 的（device_pairs 已带 userId，无需改） |

## 五、成本与风险

- **多租户插件隔离的密度**：100 个活跃用户 × 平均 3 个插件 = 300 个 fiber——cordis 单实例轻松承载（notify 扫描是唯一热点，插件数远未到阈值）；真正要防的是插件定时器滥设，加每用户 timer 上限。
- **资源计费边界**（未来）：per-user isolate 让"谁消耗的"天然可归集，为将来配额铺路。
- **冷启动体验**：首条消息触发插件实例化的路径要在 U1 卡片协议里定义好降级（实例化中→显示加载态卡片）。

## 六、一句话

云端从"功能宿主"退位为"带多租户沙箱的中转"，插件成为用户资产而非平台配置——这不仅是自定义宗旨的贯彻，还顺手解决了插件计费、配额、个性化推荐的全部前置问题，因为一切都有了 user_id。
