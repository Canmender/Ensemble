# 手机-桌面互联调研与增强方案

> 调研日期：2026-08-23 | 前置：全部代码审计（relay-server 464 行、relay-client 251 行、mobile connection.ts/discovery.ts、desktop server 集成点）
> 项目约束呼应 [[cloud-first-direction]]：不做局域网直连为主通道（但保留 zeroconf 作为辅助发现）

## 一、现状盘点（代码核实）

现有互联是**双通道并存**的架构：

```
【LAN 通道】mobile discovery.ts (mDNS _ensemble._tcp 扫描) → 直连桌面端 HTTP/WS
【云通道】 mobile connection.ts ──socket.io──▶ relay-server(8888) ◀──socket.io── desktop relay-client
```

已具备的能力：
- ✅ 设备注册/发现/顶替（同 deviceId 重连踢旧）、离线消息暂存（24h/100 条上限）、共享密钥鉴权（RELAY_AUTH_KEY，timing-safe 比较）、速率限制；
- ✅ 移动端双模式切换（`ConnectionMode = "lan" | "relay"`）+ 连接历史记录；
- ✅ 消息信封 `RelayMessage {from, to, type, payload}` 通用转发，桌面端与移动端协议对称。

**发现的缺口（按严重度排序）：**

1. ❌ **信封无端到端语义**：relay 只做盲转发是对的，但 payload 无类型约定——互联消息没有版本化 schema，双端各写一套字符串 type 约定，演进靠默契。
2. ❌ **无配对/绑定模型**：设备间靠共享 RELAY_AUTH_KEY 全局互信，没有「我的手机 ↔ 我的桌面」的设备对概念；换 key 要所有设备重新配置。
3. ❌ **断线补拉缺失（老朋友了）**：relay 暂存消息推送后即删，若移动端推送时掉线，消息就丢了——和 IM 主链路的 afterSeq 补拉是同一类问题。
4. ⚠️ LAN 发现与云通道完全独立：mDNS 找到桌面端后走的是另一套直连逻辑，两套状态机无协同。
5. ⚠️ desktop→mobile 的主动触达只有暂存一条路（移动端后台被杀时无推送唤醒集成）。

## 二、行业方案参照

| 方案 | 代表 | 对合鸣的启示 |
|---|---|---|
| **设备对 + E2EE** | Signal 的 linked devices（手机扫码绑定桌面，密钥经安全通道传输） | 配对应是一次性安全仪式而非全局密码 |
| **Continuity** | Apple Handoff（活动状态跨设备接力）、Universal Clipboard | 互联的高价值形态是「接力」不是「镜像」 |
| **通知即指令** | PushKit/FCM high-priority 唤醒 | 后台触达用推送当门铃，醒来再拉数据 |
| **就近通道优先** | AirDrop/Blob 分享：局域网 P2P 大流量、云端只走控制面 | 大文件/视频通话走 LAN，控制信令走云 |

## 三、增强方案（按优先级）

### P0：互联协议版本化 + 断线补拉（1-2 天）

1. **RelayEnvelope 加 schema**（shared 包新建 `protocol/device-link.ts`）：

```ts
export interface DeviceLinkEnvelope<T = unknown> {
  v: 1;                          // 协议版本
  msgId: string;                 // 幂等键（接收端去重）
  pairId: string;                // 设备对标识（见 P1）
  from: { deviceId: string; name: string; type: "mobile" | "desktop" };
  kind: DeviceLinkKind;          // 枚举：sync.request / sync.delta / handoff / notify / call.signal ...
  payload: T;
  ts: number;
}
```

双端 import 同一类型定义（shared 包已有 workspace 结构，mobile 补上依赖即可——现在 discovery.ts 引用的 `@ensemble/shared-protocol` 是悬空引用，node_modules 里不存在，顺手修复为真实包）。

2. **msgId 幂等去重**：relay 暂存推送改为「推送后保留 24h + 带 delivered 标记」，移动端重连后 `sync.request {sinceTs}` → 桌面端从本地日志回放 delta。复用 IM 主链路 afterSeq 的设计模式（同构问题同构解法）。

### P1：设备配对模型（2-3 天）

- **配对流程**：桌面端显示 6 位数字码（或二维码，内含桌面 deviceId + 一次性公钥指纹）→ 手机输入/扫码 → 双方在 relay 上完成挑战应答 → 服务端 `device_pairs` 表记录 `(userId, desktopId, mobileId, pairedAt)` → 后续互联信令带 pairId。
- 好处：①设备关系显式化，互联功能只对已配对设备开放；②换手机只需重新配对，不用全员换 key；③为将来 E2EE 互联消息（Signal linked-device 模式）预留了密钥协商位置——配对时的公钥交换就是 X3DH 的入口。
- 存储：主服务器 SQLite 新表（增量迁移），relay-server 不存业务数据的原则不破坏。

### P2：接力（Handoff）场景（2 天）

最高价值的互联功能，直接服务多 agent 工作流：

- **会话接力**：手机上看到一半的 run → 「在桌面继续」按钮 → handoff 消息（runId + 滚动位置 + 草稿）→ 桌面端深链打开。反向同理（桌面上开始的任务推给手机看进度）。
- 实现：kind: "handoff" 信封 + 两端的深链路由（mobile 已有 expo scheme 能力；desktop 是 Electron，加 protocol handler 即可）。

### P3：后台触达（2 天，依赖推送基建现状）

- 移动端后台被杀时：relay 暂存 + 个推/FCM 高优先级通知当「门铃」，App 醒来后走 P0 的 sync.request 拉全量——推送只是信号不是数据（IM 调研结论的直接复用）。
- 需先核实个推在互联消息路径上的接入点（现有 getui.config 是 gitignored 凭据，说明推送基建已在）。

### P4：LAN 辅助通道协同（远期）

mDNS 发现已达时，大流量（文件/视频）提示走局域网直连、控制信令保持云通道——AirDrop 模式。与 cloud-first 方向不冲突：云是默认与兜底，LAN 是优化项且需用户确认。
