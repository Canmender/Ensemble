# 合鸣插件化重构实施手册（范围内版）

> 编制日期：2026-08-23 | 前置文档：《Cordis应用方案》《功能插件系统方案》《Cordis官方教程精读》
> 约束（"范围内"的定义）：WS 协议零变化、21 个 REST 路由契约零变化、数据库 schema 零破坏性变更、每步独立提交且测试可验、随时可停在任何一步
> 全部代码位置经本轮重新核实

## 总览：五个 PR，每个半天到两天

| PR | 内容 | 工时 | 依赖 |
|---|---|---|---|

## R0：补拉参数名 bug（立即做）

`api/routes/runs.ts:32` 的 `Number(req.query.afterSeq ?? 0)` 改为 `Number(req.query.afterSeq ?? req.query.since ?? 0)`——服务端同时兼容两个参数名，移动端无需发版。加一个单测锁定。

## R1：引入 cordis 与骨架（半天）

**1. 依赖**：`pnpm add cordis zod@^3.24`（ESM 兼容已核实：cordis ESM-only ↔ server `"type": "module"`；zod 先 `pnpm ls zod` 核实解析版本）。

**2. 新文件 `src/kernel/context.ts`**：

```ts
import { Context } from "cordis";

/** 应用根上下文 —— 所有服务的宿主 */
export function createKernel(): Context {
  return new Context();
}
```

**3. 新文件 `src/kernel/pluginHost.ts`**（本 PR 只建骨架）：

```ts
import type { Context } from "cordis";
import { logger } from "../util/logger";

export interface PluginManifest {
  id: string;                 // 教程精读 §2.4：loader 按 id 区分修改/重挂
  name: string;
  version: string;
}

export class PluginHost {
  constructor(private root: Context) {}
  async loadAll(dir: string): Promise<void> { /* R4 实现 */ }
  /** 教程精读 §2.2：PENDING 诊断器 —— 启动后打印未就绪插件 */
  diagnosePending(): void {
    setTimeout(() => {
      for (const runtime of this.root.registry.values()) {
        for (const fiber of runtime.fibers) {
          if (fiber.state === "pending") logger.warn(`plugin ${fiber.name} PENDING`);
        }
      }
    }, 500);
  }
}
```

**4. context.ts 改造（最小侵入）**：`createAppContext()` 开头创建 kernel，结尾把现有返回对象原样保留——**AppContext 接口与所有消费方零改动**。kernel 此时只是被持有、未接管任何东西。

验收：`pnpm test` 全绿（appContext.test.ts / store.test.ts / engine.test.ts），启动行为无差异。回滚：revert 单提交。

## R2：核心服务 Service 化（1-2 天）

改造顺序按依赖深度从浅到深，每个服务一个 commit：

**① ConfigManager → `ctx.config`**
```ts
export class ConfigManager extends Service {
  static inject = [];   // 最浅，先改
  constructor(ctx: Context, env: ServerEnv) { super(ctx, "config"); ... }
}
```
写锁队列、缓存逻辑原样保留。改完后 createAppContext 里 `new ConfigManager(env)` 变为 `ctx.plugin(ConfigManager, env)`。

**② Store / UserStore**：无依赖包装类，直接继承 Service 注册（store.ts 不 import hub/engine，已核实是纯 db 包装）。

**③ WsHub → `ctx.hub`**：attach() 保持不变（HTTP server 由 app 层传入）；`onDeviceStatus`/`onClientMessage`/`onCallSignal` 三个回调字段**此 PR 保留**（R3 才换成事件）。hub.close() 改由 `[Service.init]` 生成的 effect 承担。

**④ OrchestrationEngine → `ctx.engine`**：构造参数 `(store, registry, hub, workflowGetter)` 改为 inject `['store','adapters','hub','config']`。

**⑤ 定时器 effect 化**：context.ts:171 的维护 setInterval 改 `ctx.interval(24h)`（cordis timer 包或自写 8 行 effect 版），手动 `clearInterval(maintenanceTimer)` 删除。

**⑥ dispose 函数退役**：`dispose: async () => {...}` 五步手工清理改为 `root.dispose()`——框架逆序自动清理。这是 R2 完成的标志：createAppContext 从 296 行降到 ~120 行以内。

**验收**：全测绿 + 手动冒烟（启动→建会话→发消息→关停进程无残留句柄警告）。**风险点**：Service 构造即注册的时序变化可能暴露隐藏初始化顺序假设——用 appContext.test.ts 的断言兜底。

## R3：消息事件总线 + RouterRegistry（1 天）

**1. 类型化事件声明**（`src/kernel/events.ts`）：

```ts
declare module "cordis" {
  interface Events {
    /** chat/message 由 engine 在落库后 emit；hub 监听并广播（替代直调） */
    "chat/message"(payload: ChatMessagePayload): void;
    "device/status"(userId: string, d: DeviceInfo, online: boolean): void;
    /** HITL 确认：serial 式异步短路；返回对象=决策（含拒绝），undefined=交给下游 */
    "tool/confirm"(runId: string, tool: string, args: unknown): Promise<{ approved: boolean } | undefined>;
  }
}
```

**2. 三处接线反转**：
- `engine.broadcastChatMessage` 尾部的 `this.hub.broadcast(...)` 改为 `this.ctx.emit("chat/message", payload)`；hub 内新增 `ctx.on("chat/message", m => this.broadcast(m.runId, 0, {...}))`。
- `hub.onDeviceStatus` 回调字段删除 → context.ts 里改为 `ctx.on("device/status", ...)` 写设备表。
- `requestConfirm` 改为派发 `ctx.serial("tool/confirm", ...)`：UI 监听器返回 `{approved}` 即短路；无人应答超时后返回 undefined → 默认拒绝。（bail 语义里 false 不是短路值，所以决策必须包对象——教程精读核实过的语义。）

**3. RouterRegistry**（~40 行）：`register(path, router)` 收集，app.ts 装配段末尾统一 `for (const [p, r] of registry) app.use(p, r)`。现有 21 个路由迁移为启动时的注册者清单——**路径与中间件顺序一字不变**。

**4. 广播面开放给插件**：PluginHost 增加 `contributes.events.on` 校验——插件只允许监听白名单前缀事件（`chat/*`、`run/*`），emit 必须带自己插件 id 前缀。

验收：全测绿 + WS 协议字节级不变（抓一帧对比）+ 移动端回归聊天/设备上下线。

## R4：第一个真实插件 + 管理 API（1-2 天）

**1. `plugins/daily-reminder/`（官方示例插件，教程第 7 章同构）**：

```
plugins/daily-reminder/
├── ensemble.plugin.json    # { id, contributes: { events.on:["chat/message"], scheduled:[...] } }
├── index.ts                # apply(ctx)：ctx.interval 定时 → ctx.emit("chat/message", ...)
└── README.md
```

**2. PluginHost.loadAll 实现**：扫描 plugins/ 目录 → manifest 校验（zod）→ `ctx.plugin(loadManifest)` → 启动日志打印各插件状态（ACTIVE/PENDING）。

**3. 管理 API**（挂在现有 auth 中间件之后）：`GET /api/plugins`（列表+状态）、`POST /api/plugins/:id/disable`、`POST /api/plugins/:id/enable`——启停即 fiber dispose/reload。

**4. 设置页「插件」卡片**：web 端列表 + 开关（消费 GET/disable/enable 三个接口即可起步）。

**验收试金石（教程精读结论）**：disable 插件后其定时器/监听器全部消失（进程内 setInterval 计数归零）；enable 后恢复；卸载无残留。

## 明确不做（范围外）

- 远程市场/沙箱加载（第二期）
- 客户端卡片协议（《用户插件与本地UI呈现方案》U 系列）
- relay-server 改造
- 数据库 schema 变更（plugin_kv 表在 R4 按需加，属增量非破坏）

## 每步回滚方式

R0-R4 各自独立 commit；任一步出问题 `git revert` 该步即可，不影响已完成步骤的价值沉淀。R1 完成后系统即处于"cords 在场但未接管"的安全态，可以无限期停留。
