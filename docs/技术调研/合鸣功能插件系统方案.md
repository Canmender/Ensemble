# 合鸣功能插件系统方案：用 Cordis 为应用补装能力

> 编制日期：2026-08-22（接续《Cordis应用方案-服务端插件化》——那篇解决"架构怎么插件化"，本篇解决"插件生态怎么长出来"）
> 依据：服务端代码审计（app.ts 路由装配、ToolRegistry、McpManager、SkillStore、WsHub 公开面）+ Cordis 三轮调研

## 一、定位：插件补什么功能

合鸣核心 = IM + 多 Agent 编排。核心保持精简，以下能力全部走插件：

| 类别 | 候选插件 | 说明 |
|---|---|---|
| **聊天互动** | 投票/接龙、日程/提醒、翻译跟帖 | 群聊里的结构化交互消息，微信小程序式场景 |
| **自动化** | 定时日报、群摘要、消息自动回复 | 定时任务 + 读历史消息 + 调 LLM |
| **外部集成** | GitHub 通知、邮件收发、RSS 推送 | webhook 进 + 轮询拉，双向桥接到会话 |
| **知识增强** | 个人知识库 RAG、网页剪藏 | 复用现有 memory/embedding 设施做垂直变体 |
| **Agent 能力包** | 新工具集（如画图、表格处理）、新编排模式 | 纯服务端贡献 |

判断标准：**凡是"能想象第三方想要但官方不必内置"的，都是插件**。

## 二、现有代码里已存在的四个挂载面（审计结论）

插件系统的本质是"把这几个人肉挂载点变成受控声明"：

1. **工具面**：`ToolRegistry.register()` 已可插拔（`tools/types.ts` 的 `AgentTool` 接口）——MCP 就是现成的动态工具贡献者。插件贡献工具 = 零新概念。
2. **路由面**：`app.ts:139-158` 手动 `app.use("/api/...", xxxRouter(ctx))` 挂了 21 个路由——需要一个 RouterRegistry 让插件注册子路由。
3. **消息管线面**：engine 的 `broadcastChatMessage`/`addSteering` 是直调——按 Cordis 方案阶段 2 的事件化改造后，`chat/incoming` waterfall 就是插件的拦截点（翻译、审核、摘要都挂这里）。
4. **定时面**：context.ts 里唯一的维护 setInterval 是人肉管理——插件需要 `ctx.interval()` 式的生命周期托管定时器。

外加两个已有设施直接复用：SkillStore（插件可带技能包）、settings 分层（插件配置有现成存取与写锁）。

## 三、设计：五件事

### 3.1 插件清单 manifest

```jsonc
// ensemble.plugin.json —— 借 shadcn registry-item 思路 + npm 元数据
{
  "name": "@ensemble/poll",            // 插件 id
  "version": "0.1.0",
  "displayName": "群投票",
  "contributes": {
    "tools": ["poll.create", "poll.close"],     // Agent 工具（进 ToolRegistry）
    "routes": [{ "path": "/api/plugins/poll", "router": "./api.ts" }],
    "events": {
      "on": ["chat/message"],                    // 监听事件
      "emit": ["plugin.poll.updated"]            // 自有事件（命名空间强制）
    },
    "scheduled": [{ "cron": "0 9 * * 1", "job": "weeklyReport" }],
    "settings": { /* zod schema 片段，进设置页自动渲染 */ },
    "ui": [{ "slot": "chat.composer.menu", "component": "PollButton" }]  // 客户端插槽（远期）
  }
}
```

规则：插件自有事件/存储键**必须带插件名前缀**；`ui` 插槽本期只定义协议不实现（客户端分发机制另立）。

### 3.2 加载与生命周期（Cordis 承担）

```
plugins/ 目录扫描 → manifest 解析 → ctx.plugin(loadPlugin(manifest))
                                     ├─ inject: ['store','tools','routerRegistry','settings']
                                     ├─ [Service.init] 里按 contributes 注册一切（全部走 effect）
                                     └─ 卸载 = dispose 自动撤销所有注册（cordis 核心红利）
```

- **信任分级第一期**：本地目录内插件 = 受信进程内加载（与 cordis/Harness vendor 模式一致）；远程市场下载的插件第二期再谈沙箱（utilityProcess/VM）。
- 配置变更走 fiber.update() → 自动重启该插件（cordis update waterfall），其他插件不受影响。
- 插件间依赖：manifest 声明 `requiresPlugins: []`，映射到 cordis inject 等待语义。

### 3.3 插件专属资源隔离

- 存储：每个插件一个 KV 命名空间（SQLite 单表 `plugin_kv(plugin_id, key, value)`，经 `ctx.isolate('storage')` 注入视图，插件拿不到别人命名空间——cordis isolate 语义的直接应用）。
- 凭据：插件 API key 存现有 KeyStore，id 强制 `{pluginId}.xxx` 前缀。
- 日志：logger 名即插件名（cordis logger 按 fiber 名派生，免费获得）。

### 3.4 管理 API 与 UI

- `GET/POST/DELETE /api/plugins`：列表/启停/卸载（启停 = fiber.dispose / 重新 load）。
- 设置页新增「插件」卡片：开关 + 每插件配置表单（由 manifest 的 settings schema 渲染——zod schema 在 shared 包，三端都能生成表单）。
- 审计：插件注册的工具在 agent 工具列表中带来源标记。

### 3.5 第一批官方插件（既是功能也是 SDK 验收用例）

按「简单→复杂」顺序开发，前三个验证四个挂载面全覆盖：

1. **每日一句/定时提醒**（验证 scheduled 面）：cron 触发 → 向指定会话发消息。~100 行。
2. **群聊投票**（验证 tools + routes 面）：agent 工具建投票 + REST 投票接口 + chat/message 监听渲染结果卡。
3. **GitHub 通知桥**（验证外部集成完整形态）：webhook 路由进 + 事件过滤 → 转发到绑定会话。
4. 后续候选：翻译跟帖（chat/incoming waterfall）、周报摘要（读历史+LLM）。

## 四、实施排期（挂在 Cordis 方案里程碑之后）

| 步骤 | 内容 | 前置 | 工时 |
|---|---|---|---|
| P1 | PluginHost 服务（目录扫描+manifest 校验+ctx.plugin 装配）+ KV 隔离存储 | Cordis 方案阶段 1 完成（ctx 可用） | 2 天 |
| P2 | RouterRegistry + chat/message 事件化落地（阶段 2 的产物被插件消费） | 阶段 2 | 含在阶段 2 |
| P3 | 官方插件①②（提醒+投票）+ 管理 API/设置页 | P1 | 3 天 |
| P4 | 官方插件③（GitHub 桥）+ 插件开发文档/模板仓库 | P3 | 2 天 |

总计约 1 周（不含 Cordis 方案本身的阶段 1-2）。验收判据：**卸载投票插件后，其工具/路由/定时器/监听器全部消失且无残留定时器进程**——这是 effect 化生命周期的试金石。

## 五、风险与边界

- **进程内插件 = 同信任级**：第一期只允许管理员从服务器本地目录安装，manifest 明示权限（tools/routes/events/scheduled 清单即权限清单）；远程市场必须等沙箱。
- **消息管线上插件失控风险**：waterfall 监听器必须有超时保护（单插件阻塞聊天不可接受），超时记日志并旁路。
- **与 MCP 的关系要说清**：MCP 是「外部工具协议」（跨进程、任何语言），本插件系统是「进程内能力包」（可挂路由/定时/事件，不止工具）。二者并存：MCP 继续作为工具类插件的一种来源，PluginHost 甚至可以出一个 mcp-bridge 插件统一纳管。
